## Incoming call

Two branches, decided by `hasLauncherIntent(currentPkg)` at `OverlayService.kt:329`, and **both end
with an overlay over the call screen**:

1. **In-call package has a launcher intent** (e.g. `com.google.android.dialer`). The transition is
   processed: `backgroundApp(X)` pauses the monitored app correctly, then the dialer evaluates as
   unmonitored and the engine emits `DismissOverlay` — which `executeCommand` treats as a deliberate
   no-op (`:488–490`). The lockout overlay therefore stays attached over the call. This is exactly
   **F-005**'s root cause; the call is a sharper consequence than the launcher case F-005 already
   argues, because the overlay is `MATCH_PARENT`, `TYPE_APPLICATION_OVERLAY` and **not**
   `FLAG_NOT_TOUCHABLE` (`:981–987`), so it consumes the taps that would answer or end the call.
   Handed to T018 as added consequence detail for F-005; **not re-filed**.
2. **In-call package has no launcher intent** (e.g. `com.android.server.telecom`,
   `com.samsung.android.incallui`). `:329` returns *before* `backgroundApp(oldPackage)`, so the session
   is never paused and `lastForegroundPackage` still names the monitored app. See **F-222**.

The call does not disable protection on either branch: the monitored app is behind the call UI, and
the next real app switch re-evaluates policy.

## Screen lock / unlock

`handleScreenOff()` pauses correctly — it runs the same `backgroundApp()` path as an app switch, so
usage is recorded, the remainder is saved, `ACTIVE_UNTIL`/`LOCKED_UNTIL` are cleared and the expiry
alarm is cancelled (`executeCommand` `:519–524`). Two properties are worth crediting: an already-shown
lock overlay is *not* removed on screen-off, so it is still covering the monitored app after unlock;
and `LOCKED_UNTIL` survives screen-off during a lockout, because `clearActiveSession` is only emitted
when a session is actually active.

The gap is the return trip. `handleScreenOff()` sets `lastForegroundPackage = null` (`:422`) and
nothing in the app listens for `ACTION_SCREEN_ON` or `ACTION_USER_PRESENT` — the only filter registered
is `IntentFilter(Intent.ACTION_SCREEN_OFF)` (`:216`). See **F-221**.

Mid-DB-write screen lock (tasks.md sub-item): `no-defect-found`. `logUsageAndCheckBudget()`
(`:559–623`) runs on `Dispatchers.IO` inside `serviceScope`; a screen-off neither kills the process nor
cancels that scope, the Room insert is transactional, and the budget write uses `commit()` (`:597–600`),
so a lock mid-write completes. Process-death-mid-write belongs to E1.

## Doze

**F-003 is cited, not re-filed.** The E2-specific contribution is a narrowing of when it bites, which
follows from the screen-off path above.

A session-expiry alarm exists only while a monitored app is foreground with a live session. Doze
requires the screen to be off. But screen-off runs `handleScreenOff()` → `backgroundApp()` →
`UpdateState(clearActiveSession = true)` → `SessionExpiryScheduler.cancel()`. So **on the healthy path
the alarm is cancelled before Doze can begin**, and F-003's Doze deferral cannot apply to sessions at
all. It applies only when one of these holds:

- `lastForegroundPackage` is `null` at screen-off, because `handleScreenOff()` returns immediately at
  `:416` and the armed alarm survives into Doze. **F-221 is the main way this state arises**, and a
  cold process re-armed by `onCreate` (`:157–162`) is another.
- The `ACTION_SCREEN_OFF` receiver failed to register — the registration is guarded and only logged
  (`:220–226`), so the app runs on with no screen-off handling and no user signal.
- The screen stays on. Then there is no Doze, and the residual delay is inexact-alarm batching plus
  App Standby. The app holds a persistent foreground service, which should keep it in the ACTIVE
  bucket, so this delay is expected to be small — `needs-verification`, V3.

`CleanupWorker` Doze/App Standby deferral (tasks.md sub-item): already assessed by T020, which
concluded the Doze hypothesis does not hold for an unconstrained weekly `PeriodicWorkRequest` and
filed the real defects as **F-048**. `no-defect-found` here; nothing to add from the interruption side.

VPN 24 h hold under Doze: **F-035**, cited.

## Home / recents / swipe-away

- **Home button.** The launcher foregrounds, `isHomeLauncher()` passes the `:329` filter, the monitored
  app is backgrounded and paused correctly. The overlay is not removed — F-005 again. Note the friction
  screen's own Skip button *does* dismiss and go home (`:952–958`); pressing the system Home button
  during the wait does not, and the countdown then runs to completion and grants a session, which is
  **F-095**. Both cited.
- **Recents / task switcher.** Same as Home once a new package resolves. The recents surface itself
  usually belongs to a package with no launcher intent, so it hits the `:329` early return and the
  session keeps accruing while the switcher is open — the same mechanism as F-222 branch 2, bounded to
  a few seconds here rather than a whole phone call, and therefore not separately filed.
- **Swipe-away.** `onTaskRemoved()` (`:680–704`) is the recovery path and it is broken in three ways —
  unguarded, `ELAPSED_REALTIME` instead of `ELAPSED_REALTIME_WAKEUP`, and `PendingIntent.getService`
  for a service that must be started as a foreground service. All three are **F-004**, cited. The
  `:a11y` watchdog (`GrayzoneAccessibilityService.kt:91–105`) is the redundant channel that masks it on
  the next app switch; F-004 already credits it.
- **Unfiled observation, handed to T018 (RU-04), not filed here.** `onDestroy()` calls
  `serviceScope.cancel()` (`:765`), which can cancel an in-flight `logUsageAndCheckBudget()` between the
  Room `insertEvent` (`:574`) and the `DAILY_USED_MILLIS`/`DAILY_RESET_DATE` `commit()` (`:597–600`),
  leaving a usage row with no matching budget accrual. Reached on swipe-away only when the system
  actually stops the service, but it is not interruption-specific — it applies to `ACTION_STOP`,
  `stopSelf()` and every system stop — so it belongs to the RU-04 destruction path rather than to E2.
  Recorded here so it is not silently dropped.

## Findings filed

### F-221 — The screen-off pause has no screen-on counterpart, so after every unlock the monitored app is unevaluated — no session, no budget accrual, no lock — until an accessibility event happens to arrive  [High]

- **Review unit**: RU-04 (`service`)
- **Location**: `app/src/main/java/com/grayzone/app/service/OverlayService.kt` →
  `registerScreenOffReceiver()` (lines 204–227, filter at `:216`) and `handleScreenOff()`
  (lines 415–436, `lastForegroundPackage = null` at `:422`); consumers of the cleared field at `:263`,
  `:330`, `:416`, `:567`, `:640`, `:1027`
- **Issue**: the service registers exactly one system-state filter,
  `IntentFilter(Intent.ACTION_SCREEN_OFF)`. There is no `ACTION_SCREEN_ON`, no `ACTION_USER_PRESENT`
  and no `KeyguardManager` query anywhere in `app/src` (searched). Screen-off therefore performs a
  destructive state transition — it clears `lastForegroundPackage`, the single field the whole service
  uses to mean "what the user is looking at" — and provides no path back. Resumption is delegated
  entirely to the next `TYPE_WINDOW_STATE_CHANGED` event, the only event type
  `GrayzoneAccessibilityService` subscribes to (`:44`), which the app never confirms it received. If
  unlocking back into an already-resumed activity does not regenerate that event on a given OEM build
  (keyguard dismissal changes window *focus*, which is `TYPE_WINDOWS_CHANGED` territory, and the
  keyguard's own events carry `com.android.systemui`, which is filtered out at `:329` for having no
  launcher intent), the service stays blind. Two independent protections then fail silently: (1) the
  paused session is never resumed, so `sessionStartTime` stays `0`, `backgroundApp()` computes
  `bgDuration = 0`, **no usage is recorded and the daily budget never accrues** — the user has
  unmetered access to the monitored app for as long as they stay in it; (2) if a lockout expires during
  the screen-off, `LockPresentation.onCountdownFinished()` sees `isStillForeground() == false`, so it
  dismisses the lock and skips `showFriction()` — the "Don't grant silent, untracked access" guard
  (`LockPresentation.kt:20–21`) inverts into exactly the silent untracked access it names. The user
  unlocks into an unblocked app. There is no log, no notification and no UI signal in either case.
- **Trigger condition**:
  1. Monitor an app X with a 10-minute session and the 15-minute minimum lockout; grant overlay and
     accessibility permissions.
  2. Open X, sit through the friction wait so a session starts. Confirm the countdown notification.
  3. Lock the screen with the power button. Confirm the pause landed:
     `adb logcat -s Grayzone | grep "Screen off - paused session"`, and
     `adb shell dumpsys alarm | grep -i grayzone` should now show no session-expiry alarm for X.
  4. Wait 30 s, unlock, and land back in X **without switching apps**.
  5. Observe whether any `App changed` / `Foreground app changed` line appears for X in
     `adb logcat -s Grayzone`. If none does, scroll inside X for two minutes, then leave it and check
     `adb shell "run-as com.grayzone.app cat /data/data/com.grayzone.app/shared_prefs/*.xml"` — with the
     defect present, `daily_used_millis_X` is unchanged and no `active_until_X` was ever written.
  6. Lockout half: repeat with X in LOCK state, lock the screen, wait past `locked_until`, unlock, and
     observe that X is usable with no friction screen and no session record.
- **Blast radius**:
  - *Callers*: `handleScreenOff()` has exactly one caller, the anonymous `BroadcastReceiver` at
    `:207–211` registered by `registerScreenOffReceiver()` (`:204–227`), itself called once from
    `onCreate()` (`:168`). The cleared field `lastForegroundPackage` is read at `:263`
    (`performMidnightReset`), `:330` and `:332` (`processForegroundAppChanged`), `:416`
    (`handleScreenOff`'s own early return), `:567` (`logUsageAndCheckBudget`'s budget-lock foreground
    test), `:640` (`handleSessionExpired` → `SessionExpiryDecision.isForegroundPackage`) and `:1027`
    (`CountdownFinishContext.isStillForeground`); written at `:351` and `:422`. All seven readers
    observe the null.
  - *Process death*: identical end state by a second route — the field is in-memory only
    (`@Volatile`, `:121`), so a restart also leaves it `null` until the next accessibility event.
    `onCreate` re-arms expiry alarms from prefs (`:157–162`) but does **not** re-seed
    `lastForegroundPackage`, so the fix must seed it on start as well as on unlock.
  - *Config change*: none. Screen-off/on is not a configuration change for the overlay window.
  - *Foreground/background*: the defect is precisely a foreground-tracking gap. It manifests while the
    app under test is foreground and Grayzone believes nothing is.
  - *Cross-process*: yes. `lastForegroundPackage` is fed exclusively from `:a11y` via
    `ACTION_APP_CHANGED` (`GrayzoneAccessibilityService.kt:86–89`) and the watchdog intent (`:93–105`),
    and is cleared in the default process by a receiver `:a11y` knows nothing about. The two processes
    therefore hold different beliefs about what the user is looking at, and only `:a11y` can correct it.
  - *Persistence*: none directly — that is the harm. Nothing is written, so the missing usage is
    invisible to `UsageDatabase` and to `DailyBudget` alike.
  - *Release-only*: no.
- **Fix** (minimal): make the receiver symmetric. Extend the filter at `:216` to
  `IntentFilter().apply { addAction(Intent.ACTION_SCREEN_OFF); addAction(Intent.ACTION_USER_PRESENT) }`,
  and in the receiver branch on the action: `ACTION_SCREEN_OFF → handleScreenOff()`,
  `ACTION_USER_PRESENT → handleScreenOn()`. `handleScreenOn()` re-seeds foreground state from the
  package the service last paused — keep the value cleared at `:422` in a `pausedPackage` field and
  feed it to the existing `handleForegroundAppChanged(pausedPackage)`, which already queues through
  `drainForegroundTransitions()` and re-runs the full policy evaluation. No new permission, no new
  component, and it reuses the transition queue rather than adding a second path into policy.
- **Rewrite justification**: n/a — one filter line, one branch, one field, one call into an existing
  entry point.
- **Test to add**: `jvm-unit` —
  `app/src/test/java/com/grayzone/app/policy/ScreenCycleResumeTest.kt`, asserting on
  `SessionPolicyEngine` + `SessionExpiryDecision` that the pause/resume pair is lossless: feed
  `AppBackgrounded(X, d)` on a state with `activeUntil = now + 5 min`, take the resulting
  `newSessionRemainingMs`, feed it back as `sessionRemainingMs` to `AppForegrounded(X)` and assert an
  `UpdateState` with `newActiveUntil ≈ now + 5 min` is emitted. Then assert the defect's shape
  directly: with no `AppForegrounded` replayed, no command is produced at all — i.e. the resume is
  event-driven, which is the property the service must guarantee. The service-side half
  (`ACTION_USER_PRESENT` delivery) is `instrumented` and **cannot be executed here**;
  `app/src/androidTest/java/com/grayzone/app/service/ScreenCycleResumeTest.kt` should assert that
  broadcasting `ACTION_USER_PRESENT` after `ACTION_SCREEN_OFF` re-produces a foreground evaluation for
  the paused package.
- **Existing test conflict**: none found. No existing test in `app/src/test` or `app/src/androidTest`
  exercises `handleScreenOff` or the screen receiver.
- **Verification**: `needs-verification` (evidence tier T4). Registered as **V1** below.
  - *Missing*: a device on which to observe whether unlocking into an already-resumed activity emits
    `TYPE_WINDOW_STATE_CHANGED` for that package.
  - *Procedure*: steps 1–6 above; the decisive observation is step 5.
  - *Severity effect*: if no event is emitted → **Critical** (every screen-off/unlock cycle silently
    disables session, budget and lockout enforcement for the app the user returns to, with no signal
    and no self-heal until an app switch). If the event is reliably emitted on mainstream builds →
    **Low** (a robustness gap: the app's only recovery from a self-inflicted state reset is an external
    event it neither requests nor verifies). **High** is recorded pending the test as the calibrated
    midpoint, since the outcome is known to vary by OEM and the failure mode is silent.
- **Build scope**: everyday-build
- **Constitution**: III (a state transition whose recovery depends on an external event with no
  handling for that event's absence)
- **Affected surfaces**: `handleScreenOff()` (`:415–436`) and `registerScreenOffReceiver()`
  (`:204–227`) — T018. Relationship to neighbouring records, stated so T055 does not merge them:
  **F-096** (RU-05) attacks the *shape* of `isStillForeground` (single-package equality vs
  multi-window); this finding is about the field being deliberately cleared with no restoration path,
  and survives F-096's proposed `visibleMonitoredPackages` fix unchanged, because that set is fed by
  the same accessibility events. **F-095** is the friction screen granting a session during screen-off;
  this is the converse — nothing granting or evaluating anything after screen-on.
- **Observed against**: `working-tree @ 557a963` (uncommitted:
  `app/src/main/java/com/grayzone/app/service/OverlayService.kt`,
  `app/src/main/java/com/grayzone/app/service/GrayzoneAccessibilityService.kt`)
- **Disposition**: `reported`

### F-222 — A full-screen takeover by a package with no launcher intent is filtered out before the pause runs, so an incoming call keeps burning the session and can have the lockout screen drawn over it  [High]

- **Review unit**: RU-04 (`service`)
- **Location**: `app/src/main/java/com/grayzone/app/service/OverlayService.kt` →
  `processForegroundAppChanged()` (line 329, `if (currentPkg == packageName || !hasLauncherIntent(currentPkg)) return`),
  with `hasLauncherIntent()` at `:556–557`; consequence at `handleSessionExpired()` (lines 630–657,
  `isForegroundPackage = lastForegroundPackage == packageName` at `:640`) and `showOverlay()`
  (`:981–994`)
- **Issue**: the `hasLauncherIntent` filter is a reasonable defence against transient system surfaces —
  the notification shade, the IME, a permission dialog — none of which should end a session, and it is
  correct for those. But it returns **before** `backgroundApp(oldPackage)` at `:347–349` and before
  `lastForegroundPackage` is updated at `:351`, so it applies the same "ignore this, the user is still
  in the old app" treatment to a package that has taken the whole screen. The in-call UI is exactly
  that case on the many builds where it is a separate, non-launchable package
  (`com.android.server.telecom`, `com.samsung.android.incallui`; only the branded dialer app carries the
  `MAIN`/`LAUNCHER` activity that `packageManager.getLaunchIntentForPackage` looks for). Consequences,
  in order of severity: (1) the session is never paused, so `activeUntil` keeps running and
  `sessionStartTime` keeps accruing — a 20-minute call consumes 20 minutes of the user's session and,
  via `logUsageAndCheckBudget()` on the next real transition, 20 minutes of the daily budget, for an
  app that was never on screen. (2) If the session expires mid-call, the alarm fires,
  `SessionExpiryDecision.decide` is handed `isForegroundPackage = true` because `lastForegroundPackage`
  still names the monitored app, and the outcome is `ShowLock` — a `MATCH_PARENT`
  `TYPE_APPLICATION_OVERLAY` window without `FLAG_NOT_TOUCHABLE` (`:981–987`) is added **over the live
  call**, consuming the taps that would end it or open the keypad. The lock is not dismissed by the
  call ending either, because leaving is an app switch and `DismissOverlay` is a no-op (F-005). The
  user's escape is the status bar, which is layered above application overlays.
- **Trigger condition**:
  1. Monitor an app X with a 2-minute session (shortest that makes the timing convenient) and grant
     overlay + accessibility permissions.
  2. Determine the device's in-call package and whether it is launchable:
     `adb shell dumpsys activity activities | grep mResumedActivity` while a call is up, then
     `adb shell cmd package resolve-activity --brief <that package>`. The finding applies when no
     launcher activity is returned.
  3. Open X and sit through friction so a session starts.
  4. Place a call to the device and answer it. Watch `adb logcat -s Grayzone`: with the defect present
     there is **no** `Foreground app changed` line for the in-call package and no usage record.
  5. Stay on the call past `activeUntil` and observe the lockout overlay appearing over the call
     screen; confirm taps on the call UI do not register.
  6. Control: repeat on a device whose dialer *is* launchable and confirm the pause does happen — which
     isolates this finding from F-005, whose stuck-overlay outcome occurs on that branch instead.
- **Blast radius**:
  - *Callers*: `processForegroundAppChanged()` has exactly one caller,
    `drainForegroundTransitions()` (`:323`), fed by `handleForegroundAppChanged()` (`:304–310`) from two
    entry points — the `ACTION_APP_CHANGED` receiver (`:178–202`) and the `ACTION_APP_CHANGED_WATCHDOG`
    branch of `onStartCommand()` (`:673–675`). `hasLauncherIntent()` (`:556–557`) has exactly one main-
    source caller, this line; `isHomeLauncher()` (`:542–554`) has exactly one, `hasLauncherIntent`.
  - *Process death*: no change to the mechanism. After a restart `lastForegroundPackage` is `null`, so
    the early return simply leaves it null — the harmful stale-value form requires a live process that
    already tracked the monitored app.
  - *Config change*: none.
  - *Foreground/background*: the entire defect is a mis-classification of a foreground takeover as a
    transient overlay. A fix must keep the transient cases (shade, IME, dialogs) behaving as they do
    now, which is why the filter cannot simply be deleted.
  - *Cross-process*: yes. `:a11y` observes and broadcasts the in-call package correctly
    (`GrayzoneAccessibilityService.kt:86–89` has no such filter); the information is discarded in the
    default process at `:329`. The two processes disagree, and the accurate one is not the one that
    acts.
  - *Persistence*: yes, and wrongly. Because the pause never runs, `ACTIVE_UNTIL`/`LOCKED_UNTIL` are
    left in place and `REMAINING_MILLIS` is never written; on the next real transition
    `logUsageAndCheckBudget()` (`:559–623`) commits call time to `DAILY_USED_MILLIS + pkg` and inserts a
    `UsageEvent` row covering the call.
  - *Release-only*: no.
- **Fix** (minimal): split the two jobs the one filter is doing. Keep the early return for the current
  package (`currentPkg == packageName`), but for a package that fails `hasLauncherIntent`, run the
  pause before returning:
  ```kotlin
  if (currentPkg == packageName) return
  if (!hasLauncherIntent(currentPkg)) {
      // A non-launchable package can still take the whole screen (in-call UI). Pause the
      // monitored app, but do not adopt the package as the new foreground.
      lastForegroundPackage?.let { backgroundApp(it, prefs, now); lastForegroundPackage = null }
      return
  }
  ```
  This makes the in-call case behave exactly like screen-off, which the service already handles.
  It does mean transient surfaces (shade, IME) also pause the session; that is the conservative
  direction — a paused session resumes losslessly through the existing `sessionRemainingMs` path
  (`SessionPolicyEngine.kt:76–88`) — and it removes the stale-`lastForegroundPackage` input to
  `handleSessionExpired` that produces the overlay-over-call. **Sequencing note**: this fix writes
  `lastForegroundPackage = null` on the same path F-221 must restore from, so the two fixes must be
  written together — F-221's `pausedPackage` field is the natural place to record it here too.
- **Rewrite justification**: n/a — one guard split into two, reusing `backgroundApp` unchanged.
- **Test to add**: `jvm-unit` —
  `app/src/test/java/com/grayzone/app/policy/SessionExpiryDecisionCallTest.kt`, asserting the
  consequence at the pure boundary: `SessionExpiryDecision.decide(now = activeUntil + 1,
  activeUntil = activeUntil, lockedUntil = activeUntil + 15 min, isForegroundPackage = true,
  isGrayzoneEnabled = true, isOnBreak = false)` returns `ShowLock`, and the same call with
  `isForegroundPackage = false` returns `ClampCountdown` — pinning that the overlay-over-call outcome is
  entirely decided by whether the service paused, which is what the fix changes. The service-side half
  is `instrumented` and **cannot be executed here**:
  `app/src/androidTest/java/com/grayzone/app/service/ForegroundFilterPauseTest.kt` should broadcast
  `ACTION_APP_CHANGED` with a package that has no launcher intent and assert `REMAINING_MILLIS + pkg`
  was written. Fails before the fix (no write), passes after.
- **Existing test conflict**: none found. `SessionExpiryDecision` has existing coverage, but no case
  fixes `isForegroundPackage = true` at a boundary where the monitored app is *not* on screen, so the
  new assertions are additive.
- **Verification**: `needs-verification` (evidence tier T4). Registered as **V2** below.
  - *Missing*: a device and a real incoming call, plus confirmation that the resumed in-call package
    has no launcher activity on that build.
  - *Procedure*: steps 2, 4 and 5 above. Step 2 alone (`cmd package resolve-activity --brief`) settles
    which branch a given build takes without placing a call.
  - *Severity effect*: confirmed with the lock drawn over a live call → **High** stands (user-visible,
    safety-relevant, recoverable via the status bar, and it does not disable protection). If the
