## Cold start after force-kill

Order in the main process (`GrayzoneApplication.kt:49–76`):

1. Process guard — `:a11y` returns at `:54` (F-078).
2. `StateBackupManager.restoreIfWiped(this)` — synchronous, main thread (`:64`).
3. `validateConfiguration()` — unguarded typed getters on whatever restore just wrote (`:70`).
4. `resetRuntimeStateIfNeeded()`, deferred IO work, streak catch-up, WorkManager, backup listener.

**Force-stop** (Settings → Force stop, or `adb shell am force-stop`) is stricter than LMK: Android
suppresses sticky restarts until an explicit component start. So after force-stop, protection is off
until the user opens the app (MainScreen `LaunchedEffect`) or the device reboots (`BootReceiver`).
That is platform behaviour, not a Grayzone defect — recorded so T034 does not treat "force-stop left
protection off" as a new Critical.

**LMK / system kill** of the main process: `OverlayService` returns `START_STICKY` (`:677`), so the
system should re-create the process and re-enter `Application.onCreate`. That re-runs the restore →
validate chain. If the backup is poisoned, **every sticky restart is also a crash loop** — C7's
blast radius is not limited to user-launched cold starts. Needs verification:

- *Procedure*: install a build, enable protection, `adb shell am kill com.grayzone.app`, watch
  `adb logcat -b crash` and `dumpsys activity services com.grayzone.app`.
- *Severity effect*: sticky restart + healthy prefs → no new finding (START_STICKY works). Sticky
  restart + poisoned backup → C7 confirmed as a crash loop (already Critical). Sticky restart
  never occurs on this OEM → raises the value of F-066 / F-061, not a new ID.

VPN sticky behaviour is conditional (`AdBlockVpnService.kt:122–169`): several early-return paths use
`START_NOT_STICKY`. After a kill mid-hold, the tunnel may stay down until `reconcileVpnState` or
`BootReceiver` — both already owned.

## Warm start from Recents

Process still alive → `Application.onCreate` does **not** run. Path is:

1. `MainActivity.onResume` → `restoreIfWiped` if all-files access is present (`:47–48`).
2. `MainAppContent` re-evaluates onboarding vs MAIN on `ON_RESUME` (`:211–217`).
3. `MainScreen`'s `LaunchedEffect(Unit)` does **not** re-run (`:247–265`).

This is exactly **F-066**. E1 adds nothing except the lifecycle framing: warm start is the path
where anti-tamper restore and protection reconcile are deliberately split across two events, and
only the first fires. Process death *hides* the bug in testing (F-066's own note at its blast-radius
§Process death) — so warm-start testing is the one that matters here.

## First launch vs n-th launch

`restoreIfWiped` early-outs when `prefs.contains(ONBOARDING_COMPLETED)` (`StateBackupManager.kt:107`).

| Launch | Prefs state | Restore? |
|---|---|---|
| Genuine first install, empty storage | no key, no backup file | no-op; onboarding proceeds |
| First launch after clear-data / reinstall, leftover `/sdcard/.grayzone/` backup | no key, backup present | **yes** — anti-tamper intent |
| n-th launch | key present | skipped |

The restore-on-first-launch behaviour is intentional and correctly placed *before* any other prefs
reader. The defect is not the branch; it is what the branch feeds into: `applyInto` with no schema
gate (F-043) and unguarded getters in `validateConfiguration` (F-060). A leftover backup from an
older app version whose value *types* changed is indistinguishable from a wipe-recovery and is C7's
non-adversarial trigger — already recorded in the E1 matrix row and in findings.md as C7.

Deferred first-launch work (`seedDefaultMonitoredAppsIfNeeded`, streak catch-up) runs on `appScope`
with local `try/catch` (`:149–153`, `:163–167`). The unprotected backup flush loop and one-shot
baseline write (`:96–100`, `:128–133`) do not — that is **F-206**.

## `onCreate` ANR risk

The comment at `GrayzoneApplication.kt:61–63` says the restore is "Synchronous by design and kept
small so it never ANRs onCreate." **F-044** examined the same call site and found shared-storage
read + AES-GCM decrypt + Gson parse + blocking `commit()` on the main thread, on the same critical
path as any subsequent `startForegroundService` deadline from sticky restart or UI launch.

E1's contribution: the comment is now a **false assurance** sitting on the Critical path. T034
should present F-044 as the ANR half of the C7 cluster (F-043 + F-060 + F-044), not as an unrelated
High — a poisoned backup crashes; a large or slow backup ANRs; both are the same `onCreate:64`
call. Comment correction is part of F-044's fix, not a separate finding.

Needs verification (ANR specifically):

- *Procedure*: place a multi-megabyte decoy at the backup path (or add artificial delay in a debug
  build), force-stop, relaunch, watch `adb shell dumpsys activity | grep -A2 ANR`.
- *Severity effect*: main-thread work >5s on a mid-tier device → F-044 stays High / becomes the
  launch-blocker beside C7. Work consistently <100ms on API 29–34 → F-044 can be lowered to Medium
  (still wrong-by-construction on the UI thread, but not an observed ANR).

## State restore after system-initiated background kill

Three recovery legs, none of which cover all three protection components:

| Leg | Restarts Overlay? | Restarts VPN? | Restores accessibility? |
|---|---|---|---|
| `START_STICKY` after LMK | intended yes | conditional | no — different process |
| `BootReceiver` after reboot | yes (`:40`) | if `VPN_ENABLED` + consent (`:48–76`) | **no** (F-010) |
| `MainScreen` `LaunchedEffect(Unit)` | yes (`:257`) | via `reconcileVpnState` (`:258`) | no — OS binds `:a11y` |

**What E1 settles:** after a non-reboot process death, there is no `BootReceiver`. Recovery is
sticky-restart of Overlay (and maybe VPN) plus whatever the user triggers by opening MAIN. The
warm-start hole (F-066) means a kill that leaves the Activity instance alive in Recents is worse
than a kill that destroys the process — the opposite of what most restart testing assumes.

Accessibility loss after kill is F-010 / F-080 territory and is not re-filed. OEM kill that
suppresses sticky restarts is F-061 / E6 territory — T052 owns that wire-up gap.

## The answer (for T034 / T055)

E1 is one chain with five faces, not five unrelated findings:

1. **Brick** — F-043 → F-060 (C7): restore then unguarded validate.
2. **ANR** — F-044: same call site, healthy-but-heavy backup.
3. **Silent protection loss on warm resume** — F-066: restore without reconcile.
4. **Background work can kill the process after a healthy start** — F-206 (ex-F-062).
5. **`:a11y` isolation is a single `return`** — F-078, and reboot never restarts that leg (F-010).

Present C7 with F-044 attached. Present F-066 as the warm-start counterpart that process-death
testing will miss. Do not mint a new Critical for "force-stop leaves protection off."
