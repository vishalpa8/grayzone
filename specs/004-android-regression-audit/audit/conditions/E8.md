## New sweep — what else diverges by variant

This is the part not covered by the findings above. Result: **the divergence surface is much smaller than
expected, and that is itself the finding.**

### Every `BuildConfig` read in the app — three, total

| Site | Reference | Assessment |
|---|---|---|
| `GrayzoneApplication.kt:58` | `BuildConfig.VERSION_NAME` | Not variant-dependent. Sits inside the boot-banner `i()` call, which F-064 already proves is dead. |
| `GrayzoneLogger.kt:38` | `BuildConfig.DEBUG` | The F-064 gate itself. |
| `GrayzoneLogger.kt:78` | `BuildConfig.DEBUG` | **Commented out** — the dead Crashlytics block owned by F-074. |

**There is no `if (BuildConfig.DEBUG)` branch anywhere in application code.** This bounds F-064 precisely:
its entire blast radius is the logger. No feature, guard, or protection path changes behaviour on the
DEBUG flag, so the uncommitted `isDebuggable = false` change cost observability and nothing else. Recorded
as a **negative result**, not a finding.

### No variant-specific source sets

`app/src/debug/` and `app/src/release/` **do not exist** — zero files. There is no variant-specific code,
manifest overlay, or resource override anywhere in the project. Another negative result worth stating,
because it eliminates the most common source of debug-only behaviour.

### The build types, and the one real gap

```56:81:app/build.gradle.kts
    buildTypes {
        release {
            isMinifyEnabled = true
            isShrinkResources = true
            isDebuggable = false
            ...
        debug {
            isDebuggable = false
            ...
```

Debug and release are now **identical on debuggability and on signing** (both non-debuggable, both signed
with the release key when the keystore is present) and differ on exactly one axis: **`isMinifyEnabled` and
`isShrinkResources` are true only for release.** The comment at `:70–75` states the intent plainly —
`installDebug` should produce something interchangeable on-device with the distributed APK.

## The answer: what would release hide?

**The uncommitted change closed the cosmetic half of the gap and left the dangerous half wide open, while
making the gap look closed.** A developer running `installDebug` now gets an app with the same signature
and the same non-debuggable status as the shipped one, and the build file explicitly tells them the two
are "interchangeable." What that build does *not* exercise is R8 — and R8 is the only remaining
difference, and precisely where F-125 lives. The one class of defect that release introduces is the one
class the everyday build is structurally incapable of reproducing, and it now wears the costume of parity.

**The four facts compound, and the whole is worse than the sum.** Consider a maintainer chasing F-125 in
the field:

1. Release **behaves** differently — four `TypeToken` subclasses are gone, so Gson reads degrade silently.
2. The **logs** that would record it do not exist — `d()` and `i()` are no-ops in every variant (F-064),
   and this is the *only* thing F-064 breaks, so it breaks exactly the diagnostic channel needed here.
3. The **stack traces** that would locate it carry no line numbers (F-126).
4. The **lint gate** that might have caught the configuration is switched off for release (F-130).
5. The **debug build** cannot reproduce any of it, because minification is off — yet it looks like release.

Each of these is individually rated Medium or Low. Together they describe a build whose most dangerous
failure mode is undetectable by every mechanism the project has for detecting failures. **That is the E8
answer, and T034 should present these five as one cluster rather than five unrelated rows** — fixing any
one alone leaves the maintainer just as blind.

**The divergence here is inverted from the usual risk.** The standard concern is that a permissive debug
build hides bugs that appear in release. Here the debug build has been made *stricter* on two axes and is
still blind on the third. The cheapest single remedy is not on this list: add a `minifyEnabled` debug-like
variant, or simply require `assembleRelease` in the verification loop, so R8's output is exercised before
it ships.

## Needs verification

No device is required for any of the above — all five facts are confirmed from generated build artifacts.
The one open item belongs to F-125 and is already recorded as the audit's highest-value device check:
whether the removed `TypeToken` subclasses cause a throw, an empty collection, or nothing at runtime.
Procedure: `./gradlew installRelease "-Dorg.gradle.java.home=C:\Program Files\jdk-21.0.11"`, then unlock
an achievement, force-stop, relaunch, and check whether previously unlocked achievements survive.
Severity-per-outcome: empty-collection → **Critical** (silent user-data loss, release-only, via
`unlockAchievement`'s read-then-write-back); throw → **High** (visible failure); no effect → **Low**
(configuration hygiene only).
