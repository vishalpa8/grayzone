## Room migration — populated-data question

**Answer: yes, the instrumented test exercises populated data.**

`MigrationTest.migrate1To2` (`:28–36`):

1. Creates the DB at version 1.
2. `INSERT INTO usage_events (...)` with a full row.
3. Closes, then `runMigrationsAndValidate(..., UsageDatabase.MIGRATION_1_2)`.
4. Asserts all four index names exist.

So the E3 brief's "whether MigrationTest exercises populated data rather than an empty DB" is
**answered in the affirmative**. What the test does *not* assert is that the inserted row's columns
survive bit-identical — `runMigrationsAndValidate` checks schema, not row contents. For a migration
that is only `CREATE INDEX IF NOT EXISTS` that is sufficient; any future data-rewriting migration
would need an explicit `SELECT` assertion. Not a defect today.

**Upgrade direction** (F-041 *Issue*): non-destructive — `fallbackToDestructiveMigration()` is
deliberately omitted; migration body creates indices only.

**Downgrade direction** (F-041): installing an older APK over v2 data has no fallback — silent loss
or crash depending on path. That is the Room upgrade-path defect.

Needs verification (device): install current release → use the app → sideload an older APK with
lower `versionCode` → confirm usage history fate. Severity already High in F-041.

## Prefs upgrade — renamed and orphaned keys

From `evidence/prefs-inventory.md` and F-068:

| Legacy key | Superseded by | Still on upgraded devices? | Migration? |
|---|---|---|---|
| `grayscale_enabled` (Boolean) | `theme_mode` (String) | yes, unread | **none** |
| `budget_locked_<pkg>` (Long prefix) | removed entirely | yes, unread | **none** |

There is **no SharedPreferences migration mechanism anywhere** in the app — the only `MIGRATION_*`
symbol is Room's. `StateBackupManager` snapshots `prefs.all`, so orphans survive clear-data via the
external backup (F-068).

**Why this is E3's load-bearing answer for C7:** the Boolean→String rename escaped a
`ClassCastException` only because the *name* changed. A future in-place type change of a key that
keeps its name, restored through `applyInto` with no schema gate (F-043), is exactly F-060's boot
loop. F-068 is Low on its own; it is the canary for the Critical.

## The answer (for T034 / T055)

E3 has two independent upgrade rails:

1. **Room** — upgrade tested with data and safe; **downgrade** is F-041.
2. **Prefs + backup** — no migration rail at all; orphans (F-068) are the mild end; type-drift
   through restore (F-043→F-060) is the severe end.

T034 should present F-068 as the evidence that "we have no prefs migration," not as an isolated Low
cleanup chore — its fix (versioned key retirement) is the same mechanism that prevents the next C7.
