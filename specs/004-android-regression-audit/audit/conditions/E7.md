## Extension â€” date-keyed surfaces (the T020 deferral)

Policy deadlines are epoch-millis. Everything that keys on `"yyyy-MM-dd"` is not:

| Surface | Mechanism | Effect of TZ change that advances the local date string |
|---|---|---|
| `RuntimeSessionReset.resetIfNeeded` | `shouldResetDailyRuntimeState` compares `lastResetDateKey` to `formatDateKey(now)` | Removes every `ACTIVE_UNTIL` / `LOCKED_UNTIL` / `REMAINING_MILLIS` for all monitored apps |
| `DailyBudget.remainingMs` / `accumulateUsedMs` | `lastResetDateKey == dateKey` else treat used as 0 | Fresh daily allowance |
| `ScheduleManager` break-used-date | `BREAK_USED_DATE != getCurrentDateKey()` | Break quota resets |
| `StreakManager.previousDateKey` | `Calendar.getInstance()` parse/add | Streak day can skip or double-count |

`OverlayService` calls `RuntimeSessionReset.resetIfNeeded` on the foreground-app-change path
(`:338`), so a TZ change takes effect on the **next app switch** â€” no process restart required.

This does **not** contradict T024's "timezone change: unaffected" for the policy unit. It answers the
deferred half: the *date-key* layer is fully timezone-coupled, and that coupling is a lockout bypass.
