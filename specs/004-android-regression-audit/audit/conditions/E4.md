## Is multi-window even reachable here?

Yes, and nothing in the project opts out.

- `app/build.gradle.kts:29` â€” `targetSdk = 34`. `android:resizeableActivity` is not declared anywhere
  in `AndroidManifest.xml`, so it defaults to `true` (API 24+), and on API 31+ the platform treats
  every activity as resizeable on large screens regardless of the attribute.
- `MainActivity` declares no `android:configChanges` and no `android:screenOrientation`, so a
  fold/unfold, a split-screen entry and a pane resize each deliver a full configuration change and an
  activity recreation.
- `minSdk = 29`, so split-screen is available on every supported OS version.

## The sharp question

*Does the overlay still cover the monitored app in split-screen and across a fold, or does the
blocked app become usable in the other pane?*

The answer separates into two independent mechanisms, and the more dangerous one is not the window
geometry â€” it is that **Grayzone has no concept of two visible apps at all**.

`OverlayService` tracks exactly one `@Volatile private var lastForegroundPackage: String?`
(`OverlayService.kt:121`), fed by a single event type. `GrayzoneAccessibilityService` subscribes only
to `TYPE_WINDOW_STATE_CHANGED` (`GrayzoneAccessibilityService.kt:44`, and
`accessibility_service_config.xml:4`) and broadcasts the event's package name verbatim. In
split-screen, focusing the second pane fires `TYPE_WINDOW_STATE_CHANGED` for the *other* package
while the monitored app remains on screen and fully interactive.
`processForegroundAppChanged` (`:327`) then reads that as "the monitored app left", which is false.

That single false premise is F-230. The window-coverage question is F-231. Configuration-change
state loss in the Compose UI is F-232.

### F-230 â€” Split-screen focus change is read as "app backgrounded", pausing the session while the monitored app is still visible and interactive  [Critical]

### F-231 â€” The blocking overlay is built once against a full-screen, single-app display model and is never rebuilt on a configuration change  [High]

- **Review unit**: RU-04 (`service`)
- **Location**: `app/src/main/java/com/grayzone/app/service/OverlayService.kt` â†’

- **Issue**: the overlay window is `MATCH_PARENT Ã— MATCH_PARENT`, `TYPE_APPLICATION_OVERLAY`,
  `FLAG_NOT_FOCUSABLE or FLAG_LAYOUT_IN_SCREEN`, gravity `TOP|START` â€” a whole-display window with no

  (the window is sized and painted once, against whatever configuration existed at
  `addView`, and never re-derived).
  1. **Split-screen coverage is unmodelled.** A display-level overlay does not participate in the
     split-screen task layout, so its bounds and z-order relative to the two panes are decided by the
     platform, not by this code. Either it covers the whole display â€” in which case Grayzone blocks
     the *unmonitored* pane too, an app the user never asked to restrict â€” or it is confined/clipped,
     in which case the monitored pane stays visible next to it. The code expresses no preference and
     has no branch for either case.

     `overlayChrome()` (`:1150`), resolved once from `isNightMode(this)`; every dimension comes from
     `dp()` (`:1134`), which converts against `resources.displayMetrics` **at construction time**;
     text sizes are set in sp once. `OverlayService` never overrides `onConfigurationChanged`, so
     after an unfold onto an inner display with a different density the card keeps its old physical
     padding and type size on a screen with different metrics, and a night-mode switch while a lock
     screen is up leaves light chrome on a dark system. The lock screen is exactly the surface a user
     stares at for up to an hour, so the degradation is not hypothetical.
- **Trigger condition**:

     unmonitored pane still accepts touches.

    `logUsageAndCheckBudget()` (`:612`), from `performMidnightReset()` (`:282`) and re-entrantly via
    `CountdownFinishContext.showFriction` (`:1028`). All four presentations are affected identically.
  - *Process death*: the window dies with the process; `START_STICKY` restarts the service but
    nothing re-shows the overlay until the next foreground event, so this defect does not survive
    process death (it does not mask C1's separate `addView`-failure path).

  - *Foreground/background*: the overlay is added while the app is backgrounded and while the
    monitored app owns the screen, so no fix may depend on Activity lifecycle or on a Compose
    recomposition.
  - *Cross-process*: none directly â€” the window is owned by the main process. `:a11y` only triggers
    the show.
  - *Persistence*: none â€” no prefs or Room writes on this path.
  - *Release-only*: none â€” layout is built in code, so resource shrinking cannot alter it.
- **Fix** (minimal): override `onConfigurationChanged(newConfig)` in `OverlayService` and, when

- **Test to add**: `jvm-unit` â€”

## Examined and clean (or not-applicable)

Named explicitly so this row cannot be marked done on an empty basis (SC-008).

- **`android:resizeableActivity` / `configChanges` misuse** â€” neither attribute is set anywhere in
  `AndroidManifest.xml`. There is no attempt to opt out of multi-window and no over-broad
  `configChanges` swallowing resize events. Clean by default, and the default is the correct choice.
- **`OverlayService` window type** â€” `TYPE_APPLICATION_OVERLAY` (`:984`) is the correct, non-deprecated
  type for API 26+; the service does not use the removed `TYPE_SYSTEM_ALERT`/`TYPE_PHONE` types that
  behave inconsistently in multi-window. Clean.
- **Countdown timing across a resize** â€” the friction countdown is an in-memory second-tick
  (`:1004â€“1016`), but the *authoritative* session deadline is an epoch value in prefs plus an
  `AlarmManager` alarm (`SessionExpiryScheduler.arm`, `:1098`), so a configuration change cannot
  extend a session by losing the tick. This is a genuine positive: the design already separates
  display countdown from enforcement. (Its clock-tamper weakness is E7/C5â€“C6's finding, not E4's.)
- **Density-independent construction** â€” every dimension goes through `dp()` rather than raw pixels,
  so the layout is correct *at construction*; the defect in F-231 is purely that it is not
  recomputed, not that it is hard-coded.
- **Picture-in-picture** â€” `not-applicable`: no activity declares
  `android:supportsPictureInPicture`, and nothing calls `enterPictureInPictureMode`. Grayzone's own
  UI cannot enter PiP. Note that a *monitored* app entering PiP is the same class of defect as F-230
  (visible but unfocused) and is covered by that record's *Foreground/background* blast radius.
- **Freeform / desktop windowing** â€” folded into F-230 and F-231; it is the same "more than one
  visible app" premise and needs no separate record.
