# E5 — Accessibility conflicts (TalkBack, content descriptions)

**Feature**: `004-android-regression-audit` | **Task**: T051 | **Written**: 2026-07-31
**Merge target**: Part C row **E5** of [`../coverage-matrix.md`](../coverage-matrix.md) (merged by T055 — this
file does not edit that row)
**Observed against**: `working-tree @ 557a963` (uncommitted: `AndroidManifest.xml`,
`GrayzoneAccessibilityService.kt`, `OverlayService.kt`, `accessibility_service_config.xml`)

## Input taken from the matrix

The E5 row read `Content descriptions static; TalkBack coexistence needs-verification`. That framing
is correct but incomplete for this app, and the gap is the interesting part: Grayzone is not merely
an app that should be labelled — it **runs an accessibility service of its own** (in the `:a11y`
process, `AndroidManifest.xml:82`) and **draws a full-screen `TYPE_APPLICATION_OVERLAY` wall** over
other apps. So E5 has to answer three questions, not one:

1. Does the blocking overlay expose usable content descriptions, or is it an unlabelled wall?
2. Can a TalkBack user actually *operate* the friction and lockout screens, including the controls
   that restore protection?
3. Do two accessibility services coexist, or does enabling TalkBack interfere with Grayzone's own?

## Outcome

**`findings-reported`** — 4 findings (1 High, 2 Medium, 1 Low). Question 3 is the one that comes out
**clean** on static evidence; questions 1 and 2 are where the defects are.

**IDs used from the T050/T051 block F-230 … F-239**: `F-233` (High), `F-234` (Medium), `F-235`
(Medium), `F-236` (Low). E4/T050 uses `F-230` … `F-232`; `F-237` … `F-239` remain unused. See the

## Question 1 — Is the overlay labelled?

Partly, and by accident rather than by design. The overlay is built entirely in code
(`OverlayService.showOverlay()`, `:865–979`) from `TextView`s and one `Button`, every one of which
carries real `text`. `TextView.getText()` is what an accessibility service reads when no
`contentDescription` is set, so the app name, the title ("Pause." / "Locked."), the reflection
prompt, the countdown, the sub-text and the button label are all nominally readable. There is no
`ImageView` and no icon-only control on the overlay, so there is no unlabelled-image gap.

What is missing is everything *above* the per-widget level:

- no `View.announceForAccessibility(...)` when the wall appears;
- no `accessibilityPaneTitle` on the root `FrameLayout` (`:867`);
- no `AccessibilityManager.isTouchExplorationEnabled` check anywhere in the codebase (searched:
  `AccessibilityManager` and `isTouchExplorationEnabled` occur **zero times** in
  `app/src/main/java/com/grayzone/app`, including inside Grayzone's own accessibility service — the
  app never asks whether a screen reader is running);
- the countdown `TextView` (`:907`) is mutated once per second (`:1010`) with no
  `accessibilityLiveRegion`, so its changes are silent.

That is F-234. It matters more here than in a normal app: this overlay's entire job is to interrupt.

## Question 2 — Can a TalkBack user operate it?

This is the sharp one, and the static evidence points at a protection problem rather than an
inconvenience.

The window is added with `FLAG_NOT_FOCUSABLE or FLAG_LAYOUT_IN_SCREEN` (`:985`). `FLAG_NOT_FOCUSABLE`
means the window never takes **input focus** — so it is never the *active* window as far as an
accessibility service is concerned (`AccessibilityWindowInfo.isActive()` follows input focus), and
key events continue to reach the app behind. The blocked app therefore keeps input focus for the
entire time it is visually covered. A screen reader that drives navigation from the active window and
performs `ACTION_CLICK` on accessibility nodes — rather than by dispatching touches at screen
coordinates — is operating on the *covered* app's node tree, which the framework has not removed
simply because another window is painted over it.

The consequence, if that is how it plays out on device: a TalkBack user swipes through and activates
the blocked app's content normally, while the wall is up and Grayzone's own screen may not even be
reachable by linear navigation. That is F-233, and by the calibration in the task brief — "an overlay
a TalkBack user cannot dismiss ... is a protection failure, not a cosmetic issue" — it is filed at
High with an explicit path to Critical on confirmation.

Both directions of that outcome are defects, which is why it is filed rather than deferred: if the
overlay *is* reachable, the user still gets no announcement that it appeared (F-234); if it is not,
the block is bypassable by anyone using a screen reader.

The controls that **restore** protection live in the Compose UI, and those have a separate,
confirmable defect: every `Switch` in the app — including the master "pause all monitoring" toggle —
is a bare `Switch` inside a `Row` whose label lives in a sibling `Column`, with no
`Modifier.toggleable`/`semantics(mergeDescendants = true)` and no `contentDescription`. That is
F-235.

## Question 3 — Do the two services coexist?

On static evidence, **yes, and the code that could have got this wrong gets it right.**

- Android supports any number of simultaneously enabled accessibility services; enabling TalkBack
  does not displace Grayzone's, and Grayzone's declares no exclusive capability. Its runtime
  `AccessibilityServiceInfo` (`GrayzoneAccessibilityService.onServiceConnected()`, `:42–55`) sets
  `eventTypes = TYPE_WINDOW_STATE_CHANGED`, `feedbackType = FEEDBACK_GENERIC`,
  `notificationTimeout = 100L` and **no flags at all** — no `FLAG_REQUEST_TOUCH_EXPLORATION_MODE`, no
  `FLAG_REQUEST_FILTER_KEY_EVENTS`, no `FLAG_RETRIEVE_INTERACTIVE_WINDOWS`, and
  `canRetrieveWindowContent="false"` in `accessibility_service_config.xml:6`. It consumes nothing and
  intercepts nothing, so there is no mechanism by which it could degrade TalkBack.
- `feedbackType = FEEDBACK_GENERIC` rather than `FEEDBACK_SPOKEN` matters: on the "spoken feedback"
  category Android historically allowed only one service at a time on some OEM skins. Grayzone
  declaring `feedbackGeneric` keeps it out of TalkBack's category. This looks deliberate and is worth
  crediting.
- The detection path is robust to TalkBack being present. `ENABLED_ACCESSIBILITY_SERVICES` is a
  colon-separated list that will contain TalkBack's component alongside Grayzone's;
  `AccessibilityServiceIds.isServiceEnabled()` (`AccessibilityServiceIds.kt:18–34`) splits on `:`,
  compares package and class exactly, and accepts both the flattened and the relative class form —
  no `contains()` substring matching, so neither a false positive from TalkBack's entry nor a false
  negative from an OEM's short form. This is exactly the bug this row would normally catch, and it is
  already fixed. Credited as a positive.

The one genuine conflict found is in the opposite direction — Grayzone reaching into a *system*
accessibility setting: `clearStaleSystemGrayscale()` (`OverlayService.kt:774–784`) writes
`accessibility_display_daltonizer_enabled = 0` on every service start. That is the colour-correction
feature, which colour-blind users depend on. It is F-236.

## Findings

### F-233 — The blocking overlay is non-focusable and carries no accessibility semantics, so the blocked app may stay operable through TalkBack while the wall is up  [High]

- **Review unit**: RU-04 (`service`)
- **Location**: `app/src/main/java/com/grayzone/app/service/OverlayService.kt` →
  `OverlayService.showOverlay()`, window parameters at lines 981–987 (`FLAG_NOT_FOCUSABLE or
  FLAG_LAYOUT_IN_SCREEN`) and the root view construction at line 867
- **Issue**: the wall is drawn as a non-focusable window over an app that keeps input focus. Nothing
  in the code tells the accessibility layer that the content behind is now unavailable: the root
  `FrameLayout` sets no `accessibilityPaneTitle`, the window is never made focusable or modal, and
  the app never marks the moment of blocking with `announceForAccessibility`. For a sighted user the
  block is total because the window is painted over everything. For a screen-reader user, navigation
  and activation go through the accessibility node tree, and the covered app's tree is still there
  and still focused. If TalkBack traverses it — the behaviour this needs a device to settle — the
  user continues to read and tap the blocked app's UI with the block visually in place, and
  Grayzone's own screen may be unreachable by swipe navigation because a non-focusable window is
  never the active one. Either the block does not hold for screen-reader users, or the user is
  stranded in front of a screen they were never told appeared.
- **Trigger condition**:
  1. Enable TalkBack (Settings → Accessibility → TalkBack, or `adb shell settings put secure
     enabled_accessibility_services
     com.google.android.marvin.talkback/com.google.android.marvin.talkback.TalkBackService` appended
     to the existing value — do not overwrite it, Grayzone's own service is in the same string).
  2. Enable Grayzone's accessibility service and overlay permission; monitor an app with a 1-minute
     session and a 60-minute lockout.
  3. Open the monitored app, clear the friction screen, wait out the session so the **lockout** wall
     appears (it is the long-lived one).
  4. With the wall showing, swipe right/left repeatedly. Record what TalkBack announces: the
     overlay's own text ("Locked.", the remaining time, "← Leave App"), or the blocked app's content.
  5. If the blocked app's content is announced, double-tap an actionable element in it and observe
     whether the underlying app responds.
  6. Note whether TalkBack announced anything at all at the moment the wall appeared (step 3→4
     boundary).
- **Blast radius**:
  - *Callers*: every overlay entry point shares these window parameters —
    `executeCommand()`'s four screen commands (`:493`, `:498`, `:503`, `:508`),
    `handleSessionExpired()` (`:653`), `logUsageAndCheckBudget()` (`:612`),
    `performMidnightReset()` (`:282`), and the re-entrant `CountdownFinishContext.showFriction`
    (`:1028`). There is exactly one `addView` site (`:990`), so one fix covers all of them.
  - *Process death*: no interaction — the window and its semantics die with the process and are
    rebuilt on the next foreground event.
  - *Config change*: a fix that adds semantics must be re-applied when the view is rebuilt; see F-231
    (E4), which proposes the rebuild path this must hook into.
  - *Foreground/background*: the overlay is added while Grayzone is backgrounded, so no fix may
    depend on an Activity or on Compose semantics — it must be plain View-layer accessibility API.
  - *Cross-process*: the show is requested from `:a11y` via `ACTION_APP_CHANGED`, but the window and
    its accessibility semantics are owned by the main process. `:a11y` cannot observe whether the
    wall is announced.
  - *Persistence*: none — no prefs or Room writes on this path.
  - *Release-only*: none. R8 does not strip View-layer accessibility calls, and the layout is built
    in code so resource shrinking cannot remove it.
- **Fix** (minimal), all on the root `FrameLayout` and the window params at `:981–987`:
  1. `root.accessibilityPaneTitle = presentation.title` (API 28+; minSdk is 29, so unconditional) —
     this makes TalkBack announce the pane when it appears and gives the window a name.
  2. `root.importantForAccessibility = View.IMPORTANT_FOR_ACCESSIBILITY_YES` and
     `root.isFocusable = true`, then `root.performAccessibilityAction(ACTION_ACCESSIBILITY_FOCUS)`
     after `addView` so accessibility focus lands on the wall.
  3. Drop `FLAG_NOT_FOCUSABLE` **only if** step 1–2 prove insufficient on device — it is load-bearing
     for the Back/Home key behaviour today, so it must not be removed speculatively.
- **Rewrite justification**: n/a — three property assignments at one site.
- **Test to add**: `jvm-unit` —
  `app/src/test/java/com/grayzone/app/service/overlay/OverlayAccessibilitySemanticsTest.kt`,
  asserting that the new pure helper `overlayPaneTitle(presentation)` returns a non-blank,
  screen-specific title for all four `OverlayPresentation` implementations (so a new screen cannot be
  added without one). Fails before the fix (no such helper; nothing constrains the value), passes
  after. The behavioural half is `instrumented` and **cannot be executed here — no device or emulator
  is available.**
- **Existing test conflict**: none. No existing JVM or instrumented test asserts on window flags or
  on accessibility semantics.
- **Verification**: `needs-verification` (evidence tier T4).
  - *Missing*: a device with TalkBack. The static facts (`FLAG_NOT_FOCUSABLE`, no pane title, no
    announcement, no touch-exploration check) are confirmed from source; what needs a device is
    whether TalkBack's node traversal crosses into the covered window and whether double-tap
    activation reaches it.
  - *Procedure*: steps 1–6 above on any API 29+ device. Capture with
    `adb shell dumpsys accessibility` while the wall is up, to record the window list and which
    window is `active`/`focused`.
  - *Severity effect*: if TalkBack can read **and activate** the blocked app's content through the
    wall → **Critical** (protection silently does not apply to screen-reader users, and there is no
    signal to anyone that it does not). If TalkBack reads the blocked app but cannot activate it, or
    reaches the overlay only via touch exploration and not linear navigation → **High** (the user is
    stranded on an unannounced wall they can leave only by finding the button by touch). If TalkBack
    correctly announces the pane and confines focus to the overlay → **Low**, downgraded to the
    missing-announcement half only, which then merges into F-234.
- **Build scope**: `everyday-build`
- **Constitution**: none
- **Affected surfaces**: all four block screens (`FrictionPresentation`, `LockPresentation`,
  `BudgetLockPresentation`, `ScheduleLockPresentation`) share the single window. Related but
  distinct: C1 in `findings.md` (the swallowed `addView` failure at `:989–994`) is the case where
  there is no wall at all; F-233 is the case where there is a wall that a screen-reader user may pass
  through.
- **Observed against**: `working-tree @ 557a963` (uncommitted: `OverlayService.kt`)
- **Disposition**: `reported`

### F-234 — The overlay's countdown is not a live region and its appearance is never announced, so a TalkBack user gets no time information on the friction and lockout screens  [Medium]

- **Review unit**: RU-04 (`service`)
- **Location**: `app/src/main/java/com/grayzone/app/service/OverlayService.kt` →
  `OverlayService.showOverlay()`, the `countdownView` construction (lines 907–913), the `subView`
  construction (lines 927–932), and the per-second update loop (lines 1004–1016)
- **Issue**: the countdown and its sub-text are set once at build time and then mutated every second
  by direct `setText` on a `TextView` with no `accessibilityLiveRegion`. A `TextView` whose text
  changes does emit `TYPE_VIEW_TEXT_CHANGED`, but with no live region TalkBack does not speak it, and
  because the overlay window is not the active one (F-233) even that is unlikely to surface. The
  practical result: a screen-reader user on the friction screen has no way to know how long the wait
  is or that it is progressing, and on the lockout screen no way to hear the remaining lockout time
  short of re-exploring the screen by touch repeatedly. On the lockout screen this is the only
  information the screen carries — `LockPresentation.bodyText()` is the fixed string "You have
  reached your session limit." and `subText()` is the fixed label "Remaining lockout time"
  (`LockPresentation.kt:12–14`), so the sole variable datum is the one that is silent. A secondary
  instance: both skip labels begin with a `←` glyph — `"← I'll Skip This"`
  (`FrictionPresentation.kt:6`) and `"← Leave App"` (`LockPresentation.kt:8`) — which a screen reader
  reads out as the character name rather than as a direction cue.
- **Trigger condition**:
  1. Enable TalkBack. Configure a monitored app with a 30-second friction wait so the countdown is
     long enough to observe.
  2. Open the monitored app and let the friction screen appear.
  3. Without touching the screen, wait 10 seconds. Observe that TalkBack says nothing as the counter
     changes.
  4. Explore the screen by touch to find the counter; note that hearing the value requires
     re-touching it for every update.
  5. Repeat on the lockout screen (drive a session to expiry) and confirm the remaining-lockout value
     is equally silent.
  6. Focus the skip button and note how the leading `←` is announced.
- **Blast radius**:
  - *Callers*: the countdown loop is created once per `showOverlay()` call; the caller list is
    identical to F-233's (`:493`, `:498`, `:503`, `:508`, `:612`, `:653`, `:282`, `:1028`). The
    per-mode text comes from the four `OverlayPresentation` implementations via `countdownText()` /
    `subText()`.
  - *Process death*: none — the loop is in-memory and rebuilt with the overlay.
  - *Config change*: the live-region property must be re-set when the view is rebuilt (see F-231).
  - *Foreground/background*: the update loop runs on `Dispatchers.Main` while Grayzone is
    backgrounded; announcements must therefore come from the View layer, not from an Activity.
  - *Cross-process*: none — main process only.
  - *Persistence*: none.
  - *Release-only*: none.
- **Fix** (minimal): set `countdownView.accessibilityLiveRegion =
  View.ACCESSIBILITY_LIVE_REGION_POLITE` at construction, and give the counter a meaningful
  description rather than a bare number by setting `countdownView.contentDescription` alongside each
  `text` update (the friction screen's `"5"` should read as "5 seconds remaining"; the lockout
  screen's `formatDuration` output already reads sensibly). Move the `←` out of the button `text` and
  into a leading drawable, or leave the text and set
  `skipBtn.contentDescription = presentation.skipButtonLabel.removePrefix("← ")`. A polite live region
  on a once-per-second update is deliberately chosen over assertive so it does not talk over the
  user.
- **Rewrite justification**: n/a.
- **Test to add**: `jvm-unit` —
  `app/src/test/java/com/grayzone/app/service/overlay/OverlayPresentationSpokenTextTest.kt`,
  asserting that the new `spokenCountdownText(secondsRemaining)` on each `OverlayPresentation`
  returns a unit-bearing phrase (e.g. contains "second" or "remaining") rather than a bare numeral,
  for all four implementations and for the `0` boundary. Fails before the fix (`countdownText(5)`
  returns `"5"`), passes after.
- **Existing test conflict**: `app/src/test/java/com/grayzone/app/service/overlay/OverlayPresentationTest.kt`
  pins the visual strings — `:46` asserts `FrictionPresentation.countdownText(5) == "5"`, and `:42`
  and `:55` assert the arrow-prefixed labels `"$arrow I'll Skip This"` / `"$arrow Leave App"`. The
  live-region and `contentDescription` half of the fix is additive and touches none of them, which is
  why the fix adds a parallel spoken variant instead of changing `countdownText`. **The `←` half
  does conflict**: moving the glyph out of `skipButtonLabel` into a leading drawable would break
  `:42` and `:55`, so take the `contentDescription`-only option there, which leaves the visible label
  and both assertions unchanged.
- **Verification**: `confirmed` (evidence tier T1) for the mechanism — the absence of
  `accessibilityLiveRegion` and of any `contentDescription`/`announceForAccessibility` on the overlay
  is a static fact (searched: zero occurrences in `service/`). `needs-verification` for how audible
  the result is.
  - *Missing*: a TalkBack device to confirm nothing is spoken today and that a polite live region is
    not excessive at one update per second.
  - *Procedure*: steps 1–6 above.
  - *Severity effect*: **Medium** as filed — the user can still reach the information by touch
    exploration, so it is degraded rather than absent. It rises to **High** if F-233 confirms that
    the overlay cannot be reached by navigation at all, because then the information is genuinely
    unreachable rather than merely awkward. It does not fall below Medium: the lockout screen's only
    variable datum being silent is a real functional gap, not cosmetics.
- **Build scope**: `everyday-build`
- **Constitution**: none
- **Affected surfaces**: `FrictionPresentation`, `LockPresentation`, `BudgetLockPresentation`,
  `ScheduleLockPresentation` — all four supply `countdownText()`/`subText()` into the same views.
- **Observed against**: `working-tree @ 557a963` (uncommitted: `OverlayService.kt`)
- **Disposition**: `reported`

### F-235 — Every `Switch` in the app is unlabelled to a screen reader, including the master toggle that pauses and restores all protection  [Medium]

- **Review unit**: RU-07 (`ui`)
- **Location**: `app/src/main/java/com/grayzone/app/ui/AppsScreen.kt` → master toggle at lines
  127–131 and the per-app monitoring toggle at lines 347–351; same pattern in
  `VpnScreen.kt:216–220`, `PerAppSettingsSheet.kt:74–78`, `ScheduleSheet.kt:173–177`,
  `CustomPromptsSheet.kt:89–93`
- **Issue**: each `Switch` sits in a `Row` next to a `Column` of `Text`s that names it, but the `Row`
  carries no `Modifier.toggleable(...)` and no `Modifier.semantics(mergeDescendants = true)`, and the
  `Switch` itself has no `contentDescription`. Compose does not merge sibling nodes, so the switch is
  published as its own accessibility node with a state ("on"/"off") and a role but **no name**. A
  TalkBack user hears the label text as one node and then, separately, an anonymous switch. On
  `AppsScreen` the master toggle — whose own supporting text is "Tap to pause all monitoring" /
  "Tap to resume monitoring" (`AppsScreen.kt:121–124`) — is the control that disables every block in
  the app, and it is anonymous at the moment of activation. The per-app list compounds it: a long
  list of rows each ending in an unnamed switch means the user must rely entirely on traversal order
  to know which app they are about to unmonitor.
- **Trigger condition**:
  1. Enable TalkBack. Open Grayzone → Apps.
  2. Swipe right until focus reaches the master toggle. Note that the announcement is the switch
     state and role with no name.
  3. Continue swiping into the per-app list; note the same for each row's switch.
  4. Double-tap and confirm the toggled app is the one whose name was announced two nodes earlier —
     i.e. that correctness depends on the user having tracked traversal order.
- **Blast radius**:
  - *Callers*: not a call-graph defect. Enumerated by search — six `Switch(` call sites in
    `app/src/main/java/com/grayzone/app/ui`: `AppsScreen.kt:127` (master), `AppsScreen.kt:347`
    (per-app), `VpnScreen.kt:216`, `PerAppSettingsSheet.kt:74`, `ScheduleSheet.kt:173`,
    `CustomPromptsSheet.kt:89`. All six share the pattern.
  - *Process death*: none.
  - *Config change*: none directly; independent of F-232.
  - *Foreground/background*: none — these are in-app controls only.
  - *Cross-process*: none — main process only.
  - *Persistence*: relevant. Each `onCheckedChange` writes `SharedPreferences` immediately
    (`PerAppSettingsSheet.kt:78`, `CustomPromptsSheet.kt:93`, `AppsScreen`'s
    `grayzone_enabled`), so a mis-targeted toggle takes effect at once and there is no confirmation
    step to catch it. The master toggle has a partial guard — it refuses to turn *off* while any app
    is locked or active (`AppsScreen.kt:130`) — which limits, but does not remove, the exposure.
  - *Release-only*: none — Compose semantics are not affected by R8.
- **Fix** (minimal): hoist the click and the name onto the row. For each site, replace the bare
  `Switch(checked, onCheckedChange)` with a `Row` carrying
  `Modifier.toggleable(value = checked, role = Role.Switch, onValueChange = …)` and pass
  `onCheckedChange = null` to the `Switch`. That merges the label text into one named, stateful node
  and is the pattern Compose documents for exactly this layout. Where the row must stay
  non-clickable (the per-app row already opens a settings sheet on tap), set
  `Modifier.semantics { contentDescription = "Monitor ${app.name}" }` on the `Switch` instead.
- **Rewrite justification**: n/a — a modifier change at six sites.
- **Test to add**: `instrumented` —
  `app/src/androidTest/java/com/grayzone/app/ui/SwitchSemanticsTest.kt`, asserting via
  `composeTestRule.onNode(isToggleable())` that every toggleable node exposes a non-empty
  `ContentDescription` or `Text` in its merged semantics, for the Apps screen. **Cannot be executed
  here — no device or emulator is available.** Fails before the fix (merged semantics of the switch
  node are empty), passes after.
- **Existing test conflict**: none — no existing test queries Compose semantics.
- **Verification**: `confirmed` (evidence tier T1). The Compose semantics behaviour follows from the
  source: no `toggleable`, no `mergeDescendants`, no `contentDescription` at any of the six sites.
  No device is needed to establish that the switches are unnamed.
  - *Missing*: nothing for the mechanism; a device run would only characterise how confusing it is in
    practice.
  - *Procedure*: steps 1–4 above, for the record.
  - *Severity effect*: **Medium** as filed — traversal order gives the user enough context to work
    the controls, so this is degraded rather than broken. It becomes **High** if a device run shows
    the master toggle can be flipped without its label ever being announced in the same focus
    sweep, since silently disabling all protection is this app's worst outcome.
- **Build scope**: `everyday-build`
- **Constitution**: none
- **Affected surfaces**: the six `Switch` sites above. `Icon(contentDescription = null)` usages
  (`HomeScreen.kt:92,152`, `AppsScreen.kt:101,157`, `OnboardingScreen.kt:82,134,186`,
  `LimitsScreen.kt:134,148`, `DailyBreakCard.kt:62`, `QuickFocusCard.kt:57`, `StreakCard.kt:53`,
  `VpnScreen.kt:140,335`) were examined and are **correct** — each is decorative with adjacent text
  carrying the meaning, which is the documented convention. They are not part of this finding.
- **Observed against**: `working-tree @ 557a963` (no uncommitted changes in `ui`)
- **Disposition**: `reported`

### F-236 — `clearStaleSystemGrayscale()` writes a system accessibility setting, disabling the user's colour-correction wherever the write succeeds  [Low]

- **Review unit**: RU-04 (`service`)
- **Location**: `app/src/main/java/com/grayzone/app/service/OverlayService.kt` →
  `OverlayService.clearStaleSystemGrayscale()` (lines 773–784), called unconditionally from
  `onCreate()` (line 148)
- **Issue**: on every `OverlayService` start the app writes
  `Settings.Secure.accessibility_display_daltonizer_enabled = "0"`. That key is **colour correction**,
  a platform accessibility feature for colour-blind users — not a Grayzone-owned setting. The
  comment calls it "stuck system monochrome from older builds", which conflates the *daltonizer mode*
  (monochromacy is one of its modes) with the *daltonizer master switch* being written here: turning
  the switch off disables the user's colour correction entirely, whatever mode they chose. As shipped
  the write throws `SecurityException` because the app does not hold `WRITE_SECURE_SETTINGS` (it is
  not in `AndroidManifest.xml`), and the catch is `catch (_: SecurityException)` — so today this is
  an unreachable, permanently-failing statement, i.e. dead code by Principle I. It stops being dead
  the moment anyone grants the permission by `adb` or on a rooted device, at which point Grayzone
  silently turns off an accessibility feature it never asked about, on every service start, including
  after every boot.
- **Trigger condition**:
  1. Settings → Accessibility → Colour correction → on, with any mode selected.
  2. `adb shell pm grant com.grayzone.app android.permission.WRITE_SECURE_SETTINGS`
     (or use a rooted device — this models the "if it were ever granted" case).
  3. Force-stop Grayzone, then re-open it so `OverlayService.onCreate()` runs.
  4. Return to Settings → Accessibility and observe colour correction is now off.
  5. To confirm the as-shipped no-op instead: skip step 2, run steps 3–4, and confirm colour
     correction is untouched and a `SecurityException` was swallowed silently (nothing is logged —
     the catch body is empty apart from a comment).
- **Blast radius**:
  - *Callers*: exactly one — `OverlayService.onCreate()` at line 148. The method is private and has
    no other reference in the codebase.
  - *Process death*: amplifies it. `START_STICKY` plus the `onTaskRemoved` restart alarm (`:680–704`)

## Examined and clean (or credited as positives)

Named explicitly so this row cannot be marked done on an empty basis (SC-008).

- **Two accessibility services coexisting** — Grayzone's service requests no exclusive capability:
  `eventTypes = TYPE_WINDOW_STATE_CHANGED` only, `feedbackType = FEEDBACK_GENERIC` (not
  `FEEDBACK_SPOKEN`, which is the category that has historically been made exclusive by some OEMs),
  `canRetrieveWindowContent="false"`, and **no flags whatsoever** in the runtime
  `AccessibilityServiceInfo` — in particular no `FLAG_REQUEST_TOUCH_EXPLORATION_MODE` and no
  `FLAG_REQUEST_FILTER_KEY_EVENTS`, either of which would genuinely fight TalkBack. No static
  mechanism for interference exists. **Positive, credited.**
- **`AccessibilityServiceIds.isServiceEnabled()`** — parses the colon-separated
  `ENABLED_ACCESSIBILITY_SERVICES` list with exact package/class comparison and accepts both the
  flattened and relative class forms, instead of `String.contains()`. This is precisely the check
  that breaks when a second service (TalkBack) is in the list, and it is already correct, with the
  reasoning documented in the file header. **Positive, credited.**
- **`onInterrupt()`** (`GrayzoneAccessibilityService.kt:115–117`) — implemented as a log-only no-op,
  which is correct: the service produces no feedback to interrupt.
- **Overlay text content** — every overlay widget is a `TextView`/`Button` with real `text`, so there
  is no unlabelled-image or icon-only-control gap on the block screens. The defect is in window-level
  semantics (F-233) and change announcement (F-234), not in missing per-widget labels.
- **`Icon(contentDescription = null)` usages** — 14 sites across `ui`, each decorative with adjacent
  text carrying the meaning. This is the documented convention, not a defect. The 9 sites that *do*
  set a description — "Clear" (`AppsScreen.kt:175`), the app icon
  `Image(contentDescription = app.name)` (`:305`), "Settings" (`:341`), "Back" (`VpnScreen.kt:132`),
  "Add" (`CustomPromptsSheet.kt:131`), "Delete" (`:159` and `ScheduleSheet.kt:190`), "Share App"
  (`SettingsScreen.kt:89`) and the bottom-navigation items
  (`MainActivity.kt:287`, `contentDescription = label`) — are exactly the ones where the icon is the
  only carrier of meaning, and they are labelled correctly. **Examined, clean.**
- **RTL** — `android:supportsRtl="true"` is declared (`AndroidManifest.xml:52`). Note that the
  overlay's `←` glyphs are literal characters in Kotlin strings, not mirrored drawables, so they do
  not flip in RTL; that is a layout-direction issue owned by **A3.2 / T027**, referenced here rather
  than filed, and it is cosmetic in any case.
- **Large font / display size** — not analysed here beyond noting that the overlay sets fixed sp
  sizes (`34f`, `72f`, `17f`) on a `WRAP_CONTENT` card, so a large font scale plus a small screen
  could clip the skip button. That belongs to **A3.2 / T027** (configuration variants); flagged for
  that task rather than double-filed.
- **`:a11y` process isolation** — the accessibility service runs in a separate process and forwards
  only a package name. It performs no accessibility interaction with other apps at all (no
  `performGlobalAction`, no `AccessibilityNodeInfo` use — searched, zero occurrences), so it cannot
  conflict with a screen reader's control of other apps. **Examined, clean.**
